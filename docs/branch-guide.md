# 브랜치 가이드

## 기본 원칙

- `main`은 검증된 변경을 모으는 기준 브랜치다. 기능·수정·문서는 작업 브랜치에서
  변경하고 PR을 통해 병합한다. `main`에 직접 커밋하거나 푸시하지 않는다.
- 한 작업 브랜치는 한 PR에 대응한다. 설명 가능한 하나의 목적을 기준으로 나눈다.
  기능 구현과 그 기능의 테스트·문서는 같은 브랜치에 둔다.
- `develop` 같은 장기 통합 브랜치는 두지 않는다. 병합한 작업 브랜치는 재사용하지 않는다.
- 기본 PR 대상은 `main`이다. 배포는 PR 병합과 별도 단계다.

## 이름

브랜치 이름은 `<종류>/<주제>` 형식을 권장한다. 주제는 짧은 영어 소문자와
하이픈으로 작성하고, 실제 변경을 설명한다.

| 종류 | 용도 | 예시 |
| --- | --- | --- |
| `feat` | 새 기능 | `feat/sparkle-updates` |
| `fix` | 버그 수정 | `fix/commit-before-switch` |
| `refactor` | 동작을 유지하는 구조 변경 | `refactor/input-events` |
| `docs` | 문서·기여 안내 | `docs/branch-pr-guides` |
| `test` | 테스트만 추가·수정 | `test/composition-boundaries` |
| `chore` | 의존성·빌드·CI 관리 | `chore/macos-ci` |

긴급 수정도 `fix` 브랜치와 PR을 사용한다. 날짜·작성자 이름·`work` 같은 모호한
이름만으로 브랜치를 만들지 않는다.

## 저장소 준비와 작업 시작

1. 기존 이슈와 PR을 확인한다. 큰 기능이나 호환성 변경은 먼저 이슈에서 방향을
   논의한다. 오타나 작은 수정은 바로 PR을 제출해도 된다.
2. 쓰기 권한이 없으면 자신의 계정으로 fork한 뒤 로컬에 clone한다. 일반적으로
   자신의 fork를 `origin`, 원본 저장소를 `upstream`으로 등록한다. 쓰기 권한이
   있는 기여자는 원본 저장소에서 직접 작업 브랜치를 만들 수 있다.
3. 원본 저장소의 최신 `main`을 기준으로 작업 브랜치를 만든다. 기존 작업을
   이어가는 경우에는 해당 브랜치를 사용한다.
4. 변경 범위를 정하고 구현한다. 다른 작업의 미커밋 변경을 새 PR에 포함하지 않는다.
   여러 작업을 진행할 때는 별도 clone이나 Git worktree를 사용할 수 있다.

브랜치를 전환해도 미커밋 변경이 자동으로 분리되지는 않는다. 전환 전에 현재
변경을 확인하고 필요한 작업을 보존한다.

## 커밋과 동기화

- 커밋에는 해당 작업의 파일만 명시적으로 선택한다. 커밋 전 staged diff를 읽고
  임시 파일, 개인 설정, 키·인증 정보, 무관한 수정이 없는지 확인한다.
- 커밋 메시지는 무엇을 왜 바꾸는지 드러나는 짧은 명령형 문장으로 쓴다.
- `main` 변경을 반영할 때 혼자 사용하는 브랜치는 rebase할 수 있다. 여러 사람이
  함께 쓰는 브랜치는 합의 없이 이력을 다시 쓰지 않는다.
- 이미 공유한 브랜치를 rebase했다면 원격 상태를 확인하고 `--force-with-lease`를
  사용한다. 일반 `--force`로 다른 사람의 변경을 덮어쓰지 않는다.
- 충돌을 해결한 뒤에는 영향받은 검증을 다시 수행한다. 해결 전 결과를 최종 결과로
  사용하지 않는다.

## PR과 병합 이후

작업 브랜치를 자신의 fork 또는 쓰기 권한이 있는 원본 저장소에 푸시한다.
원본 저장소의 `main`을 대상으로 [PR 가이드](pr-guide.md)에 따라 PR을 연다.
의존 PR이 있다면 본문에 명시한다. 기본적으로 선행 PR이 병합된 뒤 후속 브랜치를
시작하며, 불가피하게 쌓은 PR은 선행 병합 후 기준 브랜치와 diff를 다시 확인한다.

병합 후 fork와 로컬 `main`을 원본 저장소에 맞춰 동기화한다. 자신의 작업 브랜치와
워크트리는 필요한 변경이 없는지 확인한 뒤 정리한다. 다른 기여자가 사용하거나
병합되지 않은 브랜치를 임의로 삭제하지 않는다.
