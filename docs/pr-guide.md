# Pull Request 가이드

## PR의 단위

한 PR에는 하나의 문제와 해결책을 담는다. 해당 기능의 테스트·문서·필요한 빌드
변경은 함께 포함한다. 무관한 리팩터링, 디자인 변경, 의존성 정리는 별도 PR로 나눈다.
파일 수보다 독립적으로 검토·병합·되돌릴 수 있는지를 기준으로 판단한다.

작업 브랜치와 PR 대상은 [브랜치 가이드](branch-guide.md)를 따른다.

## 작성 흐름

1. 작업 브랜치에서 원본 저장소의 `main`으로 PR을 연다. 구현 중이거나 먼저 의견을
   받고 싶으면 Draft를 사용한다. 완료된 작은 변경은 바로 리뷰를 요청해도 된다.
2. Draft로 시작했다면 구현·검증·자체 리뷰 후 Ready for review로 전환한다.
3. 리뷰 지적을 반영하고 영향받은 검증을 다시 수행한다. 범위가 바뀌면 제목과 본문도
   최종 변경 기준으로 갱신한다.
4. 메인테이너가 CI와 리뷰 결과를 확인하고 병합한다. 병합 후 배포·설치가 필요한지는 별도로 판단한다.

## 제목과 본문

제목은 `종류: 구체적인 변경` 형식으로 쓴다. 종류는 브랜치와 같은
`feat`, `fix`, `refactor`, `docs`, `test`, `chore`를 사용한다.

예시: `feat: 앱 시작 시 글가드 업데이트 확인`, `fix: 입력 소스 전환 전 한글 조합 확정`.

[PR 템플릿](../.github/pull_request_template.md)을 사용하고 다음 내용을 남긴다.

- **문제와 결과:** 어떤 상황에서 무엇이 불편했고, 변경 후 어떻게 동작하는가.
- **주요 변경:** 리뷰어가 알아야 할 구현과 중요한 선택만 설명한다.
- **검증:** 실제 실행한 명령·시나리오, 환경과 결과를 기록한다.
- **제약과 복구:** 미검증 항목과 이유, 사용자 조작, 되돌릴 때 고려할 점을 적는다.

관련 이슈·선행 PR이 있으면 링크한다. 자동으로 이슈를 닫는 표현은 그 이슈 전체를
해결할 때만 사용한다. 대화 기록이나 폐기한 접근을 길게 옮기지 않는다.

## 변경별 검증

| 변경 범위 | 필요한 검증 |
| --- | --- |
| 입력기·Swift 코드 | `scripts/test.sh`, `scripts/build-app.sh`, 변경 동작의 재현 시나리오 |
| 한글 조합·입력 소스 전환 | 회귀 테스트와 대상 앱에서 실제 조합·확정·삭제·전환 확인 |
| 설정·화면 | 관련 테스트와 실제 화면·상호작용 확인, 필요한 스크린샷 |
| 랜딩 페이지 | `landing/package.json`의 lint·typecheck·test·build 스크립트와 실제 브라우저 확인 |
| 서명·설치·업데이트 | 기여자는 가능한 로컬 검사와 미검증 항목을 기록. 메인테이너가 배포 환경에서 패키지 설치·입력기 활성화를 확인 |
| 문서·PR 템플릿만 변경 | 링크·경로·절차의 일관성, diff와 서식 확인. 로컬 앱 빌드 생략 이유 명시 |

동작 변경에는 회귀 테스트를 추가하거나 기존 테스트로 해당 동작이 보호되는 근거를
제시한다. 테스트를 통과시키려고 기대 동작을 약화하거나 실패를 숨기지 않는다.
문서 변경에도 GitHub에서 실행되는 CI 결과는 확인한다.

현재 저장소의 [CI](../.github/workflows/ci.yml)는 PR에서 macOS 앱 테스트와 빌드를
실행한다. 랜딩 페이지 검증이나 실제 입력·설치 검증까지 자동화되어 있다고
가정하지 않는다. 검증 범위는 [호환성 기록](compatibility.md)을 넘겨 주장하지 않는다.

테스트·빌드 통과와 실제 사용 검증을 구분한다. 미검증 항목은 이유와 영향을 적는다.
핵심 동작이 미완성이면 Draft를 유지한다. 기여자가 접근할 수 없는 서명·배포 환경의
검증은 메인테이너에게 요청한다. 범위를 줄여 병합할 경우 그 결정과
남은 작업을 PR에 명시하고, 사용자에게 완성된 기능으로 안내하지 않는다.

## 리뷰와 병합 기준

- diff에 목적과 무관한 변경, 비밀 정보, 생성된 임시 산출물이 없다.
- 기능과 테스트·사용자 문서가 일치한다. UI 변경은 실제 화면 증거를 남긴다.
- 해당 PR 최신 커밋의 CI가 통과하고, 적용되는 리뷰 지적이 해결되어 있다.
- 리뷰 후 코드가 바뀌면 영향받은 검증과 리뷰를 갱신한다. 이전 커밋의 결과를
  최신 변경까지 검증한 것으로 표기하지 않는다.
- 기본 병합 방식은 **Squash and merge**다. 병합 커밋의 제목·본문도 최종 변경을 설명한다.
- 메인테이너가 병합을 결정한다. PR 병합이 즉시 릴리스를 의미하지는 않는다.

버그가 있으면 후속 수정 PR이나 되돌리기 PR로 처리한다. 공유된 `main` 이력을
강제로 다시 쓰지 않는다. Git 변경을 되돌리는 것과 이미 설치된 PKG를 복구하는
것은 별개이므로, 설치·배포 변경에는 해당 복구 절차도 설명한다.

## 메인테이너 안내

`main`의 PR 경유, 필수 CI 검사, 강제 푸시·삭제 제한은 저장소의 보호 규칙으로
관리한다. 리뷰 승인 조건은 프로젝트의 운영 방식에 맞춘다. 외부 fork의 코드를
검증할 때 배포 자격 증명을 제공하지 않으며, 서명·공증·게시 작업은 신뢰할 수 있는
배포 환경에서 수행한다.
